# Fresh-install and Client friction log

Observed 2026-10-04 against `main` at `499f7d1474b9da442f5a30b8fd0c669647c00783`, on macOS arm64 with Colima/Docker 29.2.1. This is the artifact for [Log the friction of a fresh install and every CLI and Client surface](https://github.com/openkestrel/kestrel/issues/488), under [Map: Plan 0.4 — kestrel starts from one command](https://github.com/openkestrel/kestrel/issues/481). It records observations; [Decide which papercuts join 0.4](https://github.com/openkestrel/kestrel/issues/494) chooses scope.

Coverage is compared with [Spec: 0.4 — kestrel starts from one command](https://github.com/openkestrel/kestrel/issues/460) (the **first-run spec**) and [Spec: 0.4 — The workbench is built on AI Elements](https://github.com/openkestrel/kestrel/issues/461) (the **workbench spec**) as read on that date. “Partial” means the draft contains a broad goal but does not name this case or its acceptance behavior.

## Method and limits

A clean directory received a `git archive main`, with no `.kestrel/organization` or `.env`. Compose used a fresh named data volume, separate image tags, a separate link network, project `kestrel-friction488`, operator port 17818 and browser port 17819. Existing acceptance resources at 7738/7739 were left alone. The default deployment built from source, with the host's existing Docker layer cache; this was not a cold-build timing measurement.

```sh
KESTREL_CONTROL_IMAGE=kestrel-friction488 \
KESTREL_ENV_IMAGE=kestrel-friction488-env \
KESTREL_CLIENT_IMAGE=kestrel-friction488-client \
KESTREL_LINK_NETWORK=kestrel-friction488-link \
KESTREL_VOLUME=kestrel-friction488-data \
KESTREL_OPERATOR_PORT=17818 KESTREL_CLIENT_PORT=17819 \
docker compose -p kestrel-friction488 up -d
```

The CLI was built from the same revision with `cargo build --locked -p kestrel-client --bin kestrel`. The preinstalled `kestrel` was older (its queue help differed), so it was not used as audit evidence. Playwright 1.63.0 drove the built browser Client, allowing its untrusted local certificate for the audit only. No host CA was installed. Failure and empty-state injections used browser request interception and are marked below; they are not claimed as spontaneous server failures.

The CLI and browser each created a Workspace and a Session. Both Sessions ended failed before provisioning an Instance because no Provider Credential or Subscription Profile existed. No personal credentials were read, copied or supplied, and there was no authenticated model answer, checkout, push or pull request. The observed end of the fresh-user journey is that sign-in dead end; successful tool calls, model choices and live checkout states below are source audits, not fabricated live results. No implementation was changed.

[CLI invocations](evidence/cli.json) contain arguments, stdout, stderr and exit status for 271 invocations: help for the root, all groups and all 55 leaf commands; an unknown flag and a missing/default invocation for every leaf; empty lists; missing references; unreachable control plane; and runtime validation across command families. A runtime pass first exposed legitimate multiple-Organization ambiguity after `organization declare 'bad name'` succeeded; its second pass explicitly scoped to `audit`. Both passes are retained, rather than presenting the ambiguity results as endpoint validation.

[Compose output](evidence/compose-up.log), [CLI start](evidence/start.json), [start explanation](evidence/start.stderr), [Transcript](evidence/transcript.txt), browser text snapshots and selected screenshots preserve the reproductions. Helpers in `evidence/` are one-off audit scripts with local paths, not a new test suite.

## CLI audit interpretation

Every captured `--help` exited 0; every deliberately unknown flag exited 2. Missing required arguments also exited 2 and showed usage. Those are working behaviors. Runtime missing references generally exited 3; invalid declarations/refusals exited 4; an unreachable control plane exited 5. Commands with no required arguments did their actual default action, so the matrix labels them “missing/default”, not “all missing arguments fail”.

No GitHub integration with a real token was registered and no dispatch reached GitHub. Integration-register help and argument validation were covered; external authentication, webhook delivery, real scheduled Firings and complete Session success were not. `instance release missing` resolved a nonexistent Workspace; it destroyed no existing Instance. `organization declare 'bad name'` succeeding is not classified as a bug: the domain accepts that name and the scope error correctly quotes it.
