# Generating Rust DTO types from `openapi/operator.json`

Research checked 3 October 2026 against the generators' repositories, crates.io, docs.rs, primary issue trackers, and the keepers' own docs (`openapi/operator.json` is OpenAPI 3.1.0 with 47 paths and 127 component schemas; stats verified by reading the document). Version-and-date facts below (crate versions, release dates, download counts) were pulled from the crates.io API on 3 October 2026; behavioural claims are traced to repos, docs.rs, or issues.

Kestrel needs a leaf crate `kestrel-operator-types` shared by an axum control plane and a CLI, generated from a committed OpenAPI 3.1 document. It wants **types only** — no HTTP client, no `reqwest` — while the browser client stays on `@hey-api/openapi-ts`.

## typify (Oxide Computer)

[`typify`](https://github.com/oxidecomputer/typify) compiles JSON Schema into idiomatic Rust types; current stable release is [0.8.0, released 2026-09-09](https://raw.githubusercontent.com/oxidecomputer/typify/main/CHANGELOG.adoc) (an 0.10.0-alpha.1 pre-release exists). It is actively maintained: a 0.10.0 alpha and dependency bumps landed the week of 2026-09-28, and [$30$M+ lifetime downloads](https://crates.io/crates/typify) reflect its role inside [progenitor](https://github.com/oxidecomputer/progenitor). Direction is **document → Rust types only** — nothing else is emitted. Consumption is of a *JSON Schema* document (Draft 7, via `schemars` marshalling internally — see the maintainer's [own admission](https://ahl.dtrace.org/2026/05/10/typify2-wip) that "The JSON Schema version that typify handles is (basically) Draft 7… On other versions, such as 2020-12 which OpenAPI 3.1+ use, typify… sometimes works, and often breaks"). Typify does **not** consume OpenAPI 3.1 documents directly — Kestrel would have to extract `components.schemas` first, which loses the 3.0 → 3.1 bridge and inherits the 2020-12 mismatches.

Composition fidelity is the bug farm. `oneOf`/`anyOf` map to serde enums with ADT tagging and `allOf` merges, but the behaviour is partial: [#895](https://github.com/oxidecomputer/typify/issues/895) shows `anyOf` over string schemas emitting `#[serde(flatten)]` on a `String` (runtime panic); [#498](https://github.com/oxidecomputer/typify/issues/498) records internally tagged enums mishandled; [#1104](https://github.com/oxidecomputer/progenitor/issues/1104) records panics and enum-name collisions. Kestrel's 12 `oneOf` (7 without a discriminator) would exercise exactly this code. `format: uuid` → `uuid::Uuid` and `format: date-time` → `chrono::DateTime` are the documented dependency obligations; format→type mapping is [overridable via the `convert` setting](https://docs.rs/typify/0.0.15/typify/). Descriptions become doc comments (see [docs.rs: types "have generated documentation"](https://docs.rs/typify/0.0.8/typify/), refined by changelog entry [*Remove the original JSON Schema from generated type docs (#1066)*](https://raw.githubusercontent.com/oxidecomputer/typify/main/CHANGELOG.adoc)). Determinism: Kestrel regenerates deterministic-looking output on a pinned crate version, but changelog items such as *"small output changes such as item reordering (#1071)"* show output churns between minor versions; no version stamp is emitted. A rewrite, ["typify 2"](https://ahl.dtrace.org/2026/05/10/typify2-wip), targets proper Draft 2020-12 support but the maintainer calls it *"in the nice-to-have bucket, not the hair-on-fire bucket"* — no release date.

## progenitor (Oxide Computer)

[`progenitor`](https://github.com/oxidecomputer/progenitor) — current [0.15.0 (2026-09-10)](https://docs.rs/progenitor) — generates an opinionated **client**, and it only reads **OpenAPI 3.0.x** ([its own docs say so](https://github.com/oxidecomputer/progenitor); [`generate_api!` errors on 3.x > 3.0 with `invalid version: 3.1.0`](https://github.com/oxidecomputer/progenitor/issues/1268)). It commits the typed models to a `types` module alongside a `Client`, but there is **no types-only mode**: failing to emit the client is not offered as a [Generator setting](https://docs.rs/progenitor/latest/progenitor/struct.GenerationSettings.html), and even static-crate mode emits a `Cargo.toml` with `reqwest` and `progenitor-client` (see [README](https://github.com/oxidecomputer/progenitor/blob/main/README.md)). The generated types still depend on `progenitor-client` for the ` progenitor_client ` request/response companion types, so using it types-only would require forking the emitter. It is invoked via `generate_api!` macro, `build.rs` + `Generator::generate_tokens`, or the [`cargo progenitor`](https://github.com/oxidecomputer/progenitor) CLI producing a full standalone crate. Production users: [Oxide's own Omicron control plane](https://github.com/oxidecomputer/omicron) uses it for all checked-in API documents via [dropshot](https://github.com/oxidecomputer/dropshot) — but those specs are 3.0.x. Kestrel cannot use progenitor as-is on a 3.1 document without downgrading the version field (which requires manually lowering the file's `openapi:` field, as the [motis](https://docs.rs/motis-openapi-progenitor/0.2.2/i686-unknown-linux-gnu/motis_openapi_progenitor) project does) and accepting a client crate that pulls `reqwest` — both of which breach the constraints.

## openapi-generator's Rust generator

The [`rust` generator](https://openapi-generator.tech/docs/generators/rust) (also responsive here for `rust-axum`, a **server** generator maintained by metaswitch) has always been **client**-oriented. Current OpenAPI Generator is [7.25.0 (24 August 2026)](https://github.com/OpenAPITools/openapi-generator) with 3.1 still listed as **"beta support"** in the [README's compatibility table](https://github.com/OpenAPITools/openapi-generator#readme). It emits a whole crate by default (templates + supporting files) including a `reqwest`-based client in the default `reqwest` library; a **types-only mode does exist** via [`--global-property models`](https://openapi-generator.tech/docs/globals) (or `.openapi-generator-ignore`), which skips API and supporting-file templates — though historically buggy ([#7358](https://github.com/OpenAPITools/openapi-generator/issues/7358), fixed in 5.x). Composition: open issues document plain-string `oneOf` branches regressing into wrapper models ([#24574](https://github.com/OpenAPITools/openapi-generator/issues/24574), 7.21.0+), and `allOf`-with-annotation failures on other generators suggest shared upstream handling is still shaky. No `anyOf` specific bug surfaced in the survey. `format` handling: `date`/`date-time` → `chrono` by default (`useChrono=true` in options); mappings are user-overridable via config. `description` becomes `///` doc comments in the Rust templates. **Determinism**: `hideGenerationTimestamp` default is already `true` (see [rust.md](https://openapi-generator.tech/docs/generators/rust)), so a *pinned major* is byte-stable across machines; between releases, template changes and internal model-flag updates (e.g. the 7.24→7.25 spring/Jackson change documented in the [migration guide](https://github.com/OpenAPITools/openapi-generator/blob/master/docs/migration-guide.adoc)) can alter output. Java/JVM toolchain and shell invocation in CI makes it heavier for a Rust-only repo. Bad fit for Kestrel: wrong architectural direction (client crate), JVM dependency, and beta-grade 3.1 handling, despite the types-only mode existing.

## typed-openapi

[`typed-openapi`](https://github.com/astahmer/typed-openapi) is **TypeScript-only** — it generates just typed schemas and clients, not Rust (see its [README](https://github.com/astahmer/typed-openapi/blob/main/README.md) and [`--schemas-only` CLI flag](https://github.com/astahmer/typed-openapi#cli)). Nothing in its docs indicates a Rust target, so it cannot produce `kestrel-operator-types`. It is listed here only to close off the survey's "any other credible option" — no other project in the JavaScript ecosystem crossed into Rust generation. For TypeScript, `@hey-api/openapi-ts` remains Kestrel's chosen tool, and typed-openapi offers no advantage there.

## Document generation: utoipa, aide, dropshot + api-manager, paperclip, okapi

These run in the wrong direction for a document-first workflow: they take **Rust annotations/handlers** as input and emit an **OpenAPI document**, whose fidelity is only as good as the derive-macro path. They are the right choice when the document is an *afterthought*; they do not consume an already-written document.

- **[utoipa](https://github.com/juhaku/utoipa)** (v[6.0.0, 22 Sept 2026](https://crates.io/crates/utoipa), axum bindings in [`utoipa-axum` 0.3.0](https://crates.io/crates/utoipa-axum), ~51M downloads). Very active. It emits an OpenAPI document from `#[derive(ToSchema)]`/`#[utoipa::path]`-annotated Rust types; it does **not** consume one. Incompatible with the keep-the-document-as-source-of-truth constraint.
- **[aide](https://docs.rs/aide)** (0.15.1 stable, April 2026; actively developed; axum integration via the built-in `aide::axum` module). Same direction — its crate docs describe it as "a code-first Open API documentation generator" and state that "[c]urrently only Open API version 3.1.0 is supported", which refers to the document it *emits* from handler schemas; it has no mode that consumes an existing document.
- **[dropshot](https://github.com/oxidecomputer/dropshot) + [dropshot-api-manager](https://github.com/oxidecomputer/dropshot-api-manager)** (0.17.1 / 0.8.0, both 2026; maintained by Oxide; a fully-worked end-to-end `openapi` + `types` workflow is documented in the README). This is the pattern Kestrel would follow if it adopted Dropshot; generating a committed document from API traits. Used in production at Oxide (Omicron). But `dropshot` is an HTTP framework on par with axum, not a fork from axum, so Kestrel would have to *port* its control plane or accept a second server crate. Not a document→Rust-types path.
- **[paperclip](https://github.com/wafflespeach/paperclip)** (0.9.7 stable, 20 April 2026) — actix-web is its primary, first-class backend; no axum path is documented in its README. Direction is Rust→document. (Server-side codegen exists for OpenAPI *clients* of a paperclip-described API, not for consuming documents into Rust.)
- **[okapi](https://github.com/GREsau/okapi)** (rocket-centric; last substantive commit [19 June 2025](https://github.com/GREsau/okapi/commits/master), rocket-only). Not maintained for axum.

## Two newer document→Rust tools

- **[openapi-to-rust](https://github.com/gpu-cli/openapi-to-rust)** ([0.19.0, 26 Sept 2026](https://crates.io/crates/openapi-to-rust); first published February 2026, ~50k downloads). Explicitly supports **OpenAPI 3.0, 3.1, and experimental 3.2** — its README itemises 3.1's `type: ["X","null"]`, `prefixItems`, `$defs`, webhooks, and discriminated unions as modelled keywords ([see "OpenAPI 3.1 / 3.2 support"](https://github.com/gpu-cli/openapi-to-rust/blob/main/README.md#openapi-31--32-support)). It has a first-class **`--types-only` mode** that omits the client; groups (`types`, `client`, `server`) are selected per-mode. It *needs* to pull `reqwest` into client mode but can drop it with `--types-only`. `format` handling is rich (`chrono`, `uuid`, `url`, `bytes`, each overridable in TOML) per [its typed-scalars section](https://github.com/gpu-cli/openapi-to-rust#typed-scalars); descs become doc comments; output is deterministic with `--check` for staleness detection. It is young (creator: GPU CLI, Feb 2026) and axum 0.8 is generated among its server modes. Experimental relative to typify/progenitor; a credible but unproven option.
- **[oas3-gen](https://github.com/eklipse2k8/oas3-gen)** ([0.28.0, 23 Aug 2026](https://crates.io/crates/oas3-gen); ~30k downloads, CLI). Reads **OpenAPI 3.1.x specifically**, "types, client, or server" modes, and types-only is the default; description→doc comments; a `bon`-builder flag toggle. Also young (Oct 2025) and without production users.

## Fit for kestrel

No single generator is a clean match; the constraints (3.1.0 document, leaf types crate shared by two crates, no HTTP client, TS browser client stays on `@hey-api/openapi-ts`) pull against the mature options:

- **progenitor** is the most opinionated and best-aligned with "shareable Rust types" (used at scale at Oxide for Omicron, [omicron](https://github.com/oxidecomputer/omicron)) but **cannot read 3.1** ([#1268](https://github.com/oxidecomputer/progenitor/issues/1268)) and has no client-free mode; the client, its `reqwest` dep, and the stable `progenitor-client` runtime crate would bleed into the CLI.
- **typify** is correctly directional (types-only, deterministic, actively maintained, overridable formats) and is what `progenitor` uses under the hood — but it accepts only (roughly) Draft-7 JSON Schema, so pointing it at a 3.1 document requires a hand-rolled extraction pass that the maintainer himself calls a "sometimes works, often breaks" path for 2020-12 ([blog post](https://ahl.dtrace.org/2026/05/10/typify2-wip)); typify 2, the fix, has [no release](https://ahl.dtrace.org/2026/05/10/typify2-wip).
- **openapi-generator's rust generator** is mature, has a real types-only mode, and consumes 3.1 in beta; but it drags a JVM toolchain and a full client-crate architecture into what should be a Rust-only leaf-crate workflow.
- **openapi-to-rust** and **oas3-gen** are the only surveyed options that read 3.1 natively and can emit types-only Rust; both are young (Feb 2026 / Oct 2025), small-community, and not yet battle-tested at Oxide-scale or on an axum-adjacent control plane.
- **Document-generation options** (utoipa, aide, dropshot, paperclip, okapi) flip the source of truth to Rust annotations, which conflicts with keeping `openapi/operator.json` committed and authoritative, and (for utoipa/aide) still don't emit a separate leaf types crate.

Mature-but-wrong-direction: progenitor, typify, openapi-generator. Right-direction-but-experimental: openapi-to-rust, oas3-gen. Wrong direction entirely (a rewrite, not a fit): utoipa, aide, dropshot, paperclip, okapi.
